## 2. Verträge, Typen und Parameter

In A2 entsteht `examples/sleep-templates-v1.json` mit importierbaren Vorlagen,
ohne echte Verknüpfungen. Namen hier sind vorgeschlagene öffentliche IDs, keine
privaten Geräte- oder Personenkennungen.

| Vertrag / interne Vorlage | Ergebnis und Verantwortung |
| --- | --- |
| `device.tv_power` / `device.power` | Bool, eindeutige an/aus-Abbildung einer Quelle; unbekannter Quellzustand bleibt unknown |
| `device.pc_power` / `device.power` | ebenso; keine Aktivitäten-/Leistungsheuristik in der Vorlage |
| `day.context_next` / `day.context_at` | Tagesart des nächsten lokalen Tags; gleiche Feiertags-/Urlaubsgrundlage wie der heutige Tag |
| `sleep.auto_permission` / `daily.window` | Bool und gültiger Zeitraum für die automatische Vermutung; startet selbst nichts |
| `sleep.flow` / `sleep.flow` | einzige zustandsbehaftete Fachvorlage; enthält den portierten Planoperator und den allgemeinen Ablauf |
| `sleep.state` / `sleep.state_view` | reine Weitergabe von `sleep.flow`: Zustand, Kontext aktiv, Eintrittsherkunft, Episode, Zustandsbeginn, Frist, erster Schlafbeginn |
| `wake.plan` / `wake.plan_view` | reine Weitergabe desselben in `sleep.flow` berechneten Plans; keine zweite Berechnung |

Der Graph ist gerichtet: Quellen/Bereich 1–3 → Tages-/Freigabevorlagen →
`sleep.flow` → `sleep.state` und `wake.plan`. **Kein Eingang von `sleep.flow`
referenziert den öffentlichen Vertrag `wake.plan`.** „Weckbeginn aus wake.plan“
im Fachauftrag bezeichnet denselben intern berechneten Zeitpunkt, keine
Transportabhängigkeit zurück in den Ablauf. Die Namen der übrigen bereits
existierenden Verträge werden beim privaten A2-Paket durch Referenzen gebunden.

`state` ist Enum `awake | pre_sleep | sleep | waking`. `since_at` bezeichnet den
letzten tatsächlichen Zustandswechsel; ein reiner Reset ändert ihn nicht.
`sleep_context_active` ist exakt `state in {pre_sleep,sleep}`. Ein intern
gehaltener Zustand macht einen wegen fehlender entscheidender Evidence
unbekannten öffentlichen Wert nicht gesund.

Eintrittsherkunft: `suspected` = automatisch vermutet, `intentional` = bewusster
Vor-Schlaf-Start, `confirmed` = Schlaf-Knopf, `timeout` = Zeitablauf.
Für Weckbeginn und Rückkehr nach wach ergänzen die Vorlagen `schedule`,
`wake_signal`, `presence_away`, `pc_on`; Erststart hat `initial`. Diese Labels
sind deklarierte Texte einer Vorlage, keine eingebauten Schlafregeln.
Ein Selbstübergang mit reinem Fristreset erhält die Eintrittsherkunft;
`last_action_origin` und Nachweis nennen den neuen Knopfdruck. Insbesondere
kann ein zuvor durch Zeitablauf begonnener Schlaf nach Schlaf-Knopf eine neue
bestätigte Frist haben, ohne seinen ursprünglichen Eintritt umzudatieren.

Episode: beim Start aus `awake` neu; `sleep → pre_sleep` ausdrücklich neu;
sonst innerhalb der laufenden Folge unverändert, auch bei `waking → sleep`
oder `waking → pre_sleep`. Jeder Übergang nach `awake` beendet die Episode.
Der technische Initialzustand hat schon eine ID, öffentlich aber
`episode_active=false`. Beim nächsten Start wird sie ersetzt. Kein manueller
„wach setzen“-Befehl und kein freigeschalteter administrativer Ablauf-Neustart.

Fristen: `pre_sleep` 2.700 s, `sleep` 2.700 s ausschließlich nach Schlaf-Knopf,
`waking` 3.600 s. Ein Reset setzt **now + volle Dauer**, mit neuer ID/Generation.
`pre_sleep → sleep` durch Ablauf löscht die Frist. Das Ablaufen einer bestätigten
Schlaf-Frist beendet weder Schlaf noch Episode; der Termin wird einmal als
verarbeitet dokumentiert, es gibt keinen Zustandswechsel. Engines können daraus
später handeln. Veröffentlichung von `deadline_at` nur als laufender, noch
nicht verarbeiteter UTC-Termin; ohne Frist `not_applicable` statt gültigem null.

Parameteränderungen laufen über Entwurf → Prüfen → Übernehmen (G19/A-06),
ohne neue Vorlagenversion. Sie sind keine Laufzeit-Knopfdruckereignisse und
verlängern keine bestehende Frist stillschweigend. Semantische Änderungen an
einem Ablauf benötigen den bestehenden Kompatibilitäts-/Neuinitialisierungspfad.

fehlender Weckplan verhindert den absoluten Übergang, **nicht** die Dauerfrist.
Fehlende optionale Ereignissensoren verhindern keine andere Entscheidung.

Ein späterer echter PC-/Away-Nachweis darf anschließend normal zurücksetzen.

`pre_sleep`: PC-an-Flanke → away → Interaktion;
`sleep/waking`: frisches Wecksignal → away;
der away-Guard verwendet gemäß K1 `first_usable[location == away,false]`;
`awake`: automatische Startbedingung. False überspringt, unknown hält spätere
Alternativen an. Alle optionalen Ereigniszweige verwenden davor
`first_usable[qualifiziertes_Ereignis,false]`, mit erhaltenen Ausfallgründen.

fällige Zeitprüfungen. Bei gleichem absolutem und Dauertermin gilt die bereits
vorhandene ausdrückliche `priority:absolute`. Bei verschieden alten Terminen
gilt ADR 0015: frühester zulässiger Termin. Diese technische Reihenfolge ist
Teil des Reviewvorschlags, nicht eine behauptete Produktentscheidung zu bisher
nicht spezifizierten Gleichzeitigkeiten.

## 4. P1, P3 und P4 – Ereignisse, Commands und Fristen

P1 erweitert das Format ausdrücklich um `transition_selection:"ordered"` in
Sprachversion 6. Alte Definitionen werden weder umsortiert noch umgeschrieben.
Reihenfolge gehört zur Semantik-Prüfsumme. Ein Durchlauf nimmt höchstens einen
Eingangsübergang; Folge-Ausgänge und danach fällige Zeitregeln werden konsistent
ausgewertet. Argumentzweige eines Commands verwenden dieselbe deklarierte
Reihenfolge. Guardfehler sind Fehler, niemals false.

P3 wählt **Commands mit Fristreset**, keinen zustandsbehafteten Aktionssensor.
Die bestehenden `POST /api/v1/commands` und `GET /api/v1/commands/{command_id}`
bleiben das persistierte Ausführungsmodell. Sprachversion 6 erlaubt
`deadline_action:reset` auch für deklarierte Commands. Jeder akzeptierte neue
Command ist ein eigener Auslöser; er benötigt keine Nein→Ja-Flanke. Gleiche ID
und gleicher Inhalt liefern dasselbe Ergebnis; gleiche ID mit anderem Inhalt
ist Konflikt. Keine neue Episode als Trick, um einen Reset zu erzwingen.

Traber erhält den allgemeinen HA-Dienst **`traber.send_command`**, der vom
vorhandenen Switch Manager aufgerufen wird. Parameter:
`contract_id`, `command`, `arguments`, optionale wiederverwendete `request_id`.
Der Dienst erzeugt für einen neuen Aufruf eine UUID, erfasst HA-Prozesskennung
und Ausführungszeit und gibt eine Antwort mit ID und Ausführungsstatus zurück.
Wuschel ist bereits als authentifizierter Admin-WebSocket-Client mit Traber
verbunden. Traber liefert Command-Anfragen auf einer eigens ausgehandelten
Live-Subscription an **genau den zur Installation gehörenden Client**;
Wuschel führt sie über denselben Processor und `command_log` aus und bestätigt
das committed Ergebnis über einen zugehörigen WebSocket-Antwortaufruf.
Neue optionale Protokoll-2-Fähigkeit `command_ingress_v1`; kein neuer Token in
HA, keine URL-/Credential-Eingabe im Dienst, kein öffentlicher Event-Bus.
Die WebSocket-Kommandos für Subscription/Antwort sind adminpflichtig.

Die vollständige Hülle nach Übersetzung in Wuschel verwendet vorhandene Felder:
`command_id`, `contract_id`, `command`, `args`, `origin`, `issued_at`,
`valid_until`, `expected_registry_revision`. Traber transportiert zusätzlich
HA-Epoch/Request-Identität; Wuschel erstellt daraus die geprüfte Herkunft,
statt beliebige vom Aufrufer behauptete Adminrollen zu übernehmen. Der Client
bindet die aktive Revision bei Annahme; läuft sie vor dem Commit davon, folgt
Konflikt, kein Umdeuten auf eine neue Vorlage. Gültigkeit 30 s ab Annahme der
HA-Anfrage; Wuschel prüft Zukunft, Ablauf und aktive Installationssession.
Traber hält höchstens 64 laufende Anfragen, keine dauerhafte Zustellwarteschlange.
Bei Trennung/Neustart keine Wiedergabe und kein Senden nach Wiederverbindung.
Geht nur die Antwort verloren, wird zuerst das Ergebnis derselben ID abgefragt;
bei Wiederholung bleiben ID, Inhalt und ursprüngliche Zeiten identisch.

Der Dienst ist für nach HA-Regeln berechtigte lokale Automationen aufrufbar;
externe WebSocket-Clients brauchen Adminrechte. Backend prüft zusätzlich
Installation, aktive Session, Contract, deklarierten Command, Args-Schema,
Gültigkeit, Revision und Ratenbegrenzung. Allgemeine Schreib-/Authentifizierungs-
regeln werden durch den neuen Weg nicht abgesenkt. Keine Annahme, dass ein
HA-`user_id` menschliche Bedienung beweist. Das bewusst definierte
Switch-Manager-Mapping ist die Quelle des fachlichen Knopfdrucks.

Benni richtet später nur zwei Gesten im vorhandenen Switch Manager ein:
„Aus lang“ → `sleep.flow / confirm_sleep`, „Helligkeit runter lang“ →
`sleep.flow / start_pre_sleep`. Keine HA-Aktionsentität wird erfunden.
Dieser A1 führt den Dienst nicht aus und ändert den Switch Manager nicht.

Interaktionen aus Quellen benötigen ebenfalls Ereignisidentität: Die neue
allgemeine Regel `event_match` prüft den **aktuellen belegten** Eingangsvorgang
mit `ingest_seq`, Evidence-ID, Zeit und Runtime-Epoch. Modi `changed`,
`rising`, `falling`; für die Vorlage keine beliebige Ereignissprache.
Bei `reset_trigger:"event"` verbraucht ein Reset diese Identität genau einmal,
auch bei zwei Ereignissen vor dem bisherigen 0,5-s-Pulsende. Ein späterer Tick,
ein anderes Attribut oder ein unveränderter Bericht ist kein neues Ereignis.
Altes `reset_trigger` ohne Angabe bleibt die bestehende Flankensemantik.
Für Kontrakteingänge muss die ursprüngliche Ereignis-Evidence durchgereicht
werden; bloße Neuveröffentlichung einer identischen Wahrheit zählt nicht.

| Eingang | Interaktion in pre_sleep | Wecksignal in sleep/waking |
| --- | --- | --- |
| Flur-Präsenz | ausschließlich aus → an | nein |
| Terrassentür aus Bereich 1 | frisches Öffnen **und** Schließen | frische Kontaktänderung nach Zustandsbeginn |
| Fenster aus Bereich 1 | nein | frische Kontaktänderung nach Zustandsbeginn |
| Toilettendeckel | frischer belegter Wechsel | nein |
| Kaffeemaschine | frischer belegter Geräte-/Tasterwechsel | frisches Einschalten nach Zustandsbeginn |
| Badlicht | frischer belegter Wechsel | nein |
| Küchenschalter, falls vorhanden | frisches Tasterereignis | nein |
| Denon-Lautstärke | echte Zahlenänderung und **nicht positiv** `known_automatic` | nein |
| PC | PC-an-Flanke beendet pre_sleep | frisches Einschalten nach Zustandsbeginn |

Öffnen/Schließen eines Fensters zählt als Fensterereignis; ein schon offenes
Fenster beim Eintritt zählt nicht. Einschalten statt Ausschalten von PC/Kaffee
ist im Claude-Review bestätigt. K3 verlangt echte Nutzung durch Leistung
oder Hostaktivität, niemals den Steckdosen-Schaltzustand. Es gibt keine Phasensperre.
Direkte Sensor-/Tasterereignisse benötigen keine Herkunftsprüfung. Bei Denon
bleibt unbekannte Herkunft unbekannt und darf zählen; bekannte Automatik nicht.
Die Allowlist besteht aus gebundenen optionalen Bool-Eingängen mit diesen
allgemeinen Ereignisfiltern. Erweiterung über Konfiguration, neue Verknüpfung
und Übernahme; kein Python-Whitelist-Array mit privaten Entitätsnamen.

P4 bleibt bestehende Funktion: Fristregel für `sleep` 2.700 s, auf dem
Timeout-Übergang ausdrücklich `clear`; auf bestätigtem Eintritt normale neue
Zustandsfrist. Kombination `new_episode` plus explizitem Fristreset bleibt
ungültig; neue Episode und Zustandswechsel wählen ihre Dauer wie bisher.

## 5. P2 und Freigabe über Mitternacht

Allgemeine Projektion `calendar_at` erhält ein ausdrücklich typisiertes Datum
`YYYY-MM-DD` und liefert Wochentag/lokale Tagesgrenzen. Eine Erweiterung von
`calendar_active` erhält optional `on_date`; sie prüft Überschneidung mit dem
halboffenen lokalen Tag statt nur Aktivität jetzt. Für Urlaub zusätzlich
`all_day_only:true`. Ein gültiger leerer Bestand ist false; abgelaufener,
ungültiger oder nicht vollständig abgedeckter Tag bleibt unknown. Keine
Umdeutung eines aktuellen Feiertags-Sensors in morgigen Feiertagsnachweis.
Feiertage benötigen kalenderdatumsfähige Eingänge oder explizite Intervalle.

Der 30-Tage-Horizont des Originals prüft **heute bis einschließlich Tag +30**.
Das bestehende Kalenderfenster kann das mit `past_days:0,future_days:31`
bereits abdecken; Ende ist exklusive Mitternacht von Tag +31. Die Standard-
Vergangenheit von einem Tag darf nicht zusätzlich konfiguriert werden, weil
sonst die bestehende 31-Tage-Grenze verletzt würde. Kein Limit wird erhöht.
Ganztägige mehrtägige Termine werden auf alle betroffenen lokalen Tage
abgebildet, nicht nur auf das Startdatum. Sommer-/Winterzeit verwendet lokale
Kalendertage, niemals `now + 86400` als morgen.

Die Freigabe ist ein halboffenes Intervall `[Beginn, Ende_early_morning)` mit
einem **Nachtbezug auf das Datum des zugehörigen Morgens N**. Der Abend ist
N−1; „vor einem Arbeitstag“ wählt `day.context_at(N)==werktag`, also kein
Feiertag und kein ganztägiger Urlaub. Das bleibt nach Mitternacht derselbe
Bezug; um 00:01 wird nicht versehentlich N+1 ausgewählt.

Je zwei Parametergruppen `before_workday` und `otherwise`:
`start_kind:phase|time`, `start_phase`, `start_time`. Standard jeweils
`phase/early_night`; inaktive Auswahlfelder bleiben ohne Wirkung. Ende ist
Beginn von `forenoon`, entsprechend den vorhandenen Jahreskurven aus Bereich 3.
Die Phasenberechnung wird als gemeinsame reine Datumsfunktion/Untervorlage
wiederverwendet, keine zweite abweichende Sonnen-/Nachtformel.

Zur Intervallbildung wird für N zuerst das Ende berechnet. Die letzte
vorkommende konfigurierte Phasen-/Uhrzeitgrenze **vor** diesem Ende ist der
Beginn: eine Abendzeit liegt N−1, eine frühe Nacht-/Morgenzeit liegt N.
Identischer Beginn und Ende ist als leeres Intervall ungültig; keine
heimliche 24-h-Freigabe. Beispiel rein synthetisch: Abendbeginn 22:17 am
N−1, morgens Ende 08:41 am N; 00:00 liegt weiter darin. Bei `early_night`
kann der Beginn saisonal erst nach Mitternacht liegen; davor ist die Freigabe
false. Die Vorschau nennt immer die konkreten beiden Daten und Uhrzeiten.

Diese allgemeine `daily_window`-Auswertung plant nächste Grenze, lokalen
Tageswechsel und frühere Evidence-Gültigkeitsgrenze über die vorhandene Clock.
Unbekannte Tagesart wählt nicht heimlich „sonst“; sind beide Parametereinstellungen
identisch, darf dieser identische Zeitraum unabhängig vom Zweig benutzt werden,
mit sichtbarer Diagnose. Keine Zeitänderung erzeugt einen Knopfdruck.

Validierung: gültiges Datum, gültige `HH:MM`, geschlossene Phasenliste,
Auswahlfelder passend zum Modus, Datum innerhalb des belegten Kalenderfensters,
begrenzte Regeln und Fristen; keine freien Ausdrücke. Restore berechnet den
aktuellen Zeitraum aus Clock und gültigem Kalendercache neu. Es spielt keine
verpasste Nacht-/Tagesgrenze als Interaktion nach.

## 6. Weckplan-Port, Konfiguration und Nachweisgrenze

Normative Quellmodule am oben festgehaltenen Referenzstand:
[`wake_planning.py`](https://github.com/Levtos/benni-core-state/blob/c9408fa33f2914b1c5f7316738cb38b43add33b5/custom_components/benni_core_state/wake_planning.py)
und [`wake_config.py`](https://github.com/Levtos/benni-core-state/blob/c9408fa33f2914b1c5f7316738cb38b43add33b5/custom_components/benni_core_state/wake_config.py).
Nur der reine Plan-/Konfigurationskern wird portiert. HA-Coordinator, Legacy-
Migration, Shadow-Vergleich und `_iso_now` werden keine neue Laufzeitabhängigkeit;
Wuschel verwendet seine Clock. Die mathematische Entscheidung des Grundplans
bleibt unverändert, einschließliche der folgenden nicht offensichtlichen Details.

| Teil | Zu erhaltende Semantik |
| --- | --- |
| Profile | weekday und weekend, Samstag zählt zum Wochenende; Feiertag benutzt Wochenendprofil |
| Regeln | enabled, priority, weekdays, date_from/to inklusive, specific_dates, week_interval/anchor, cycle_anchor/length/slot_start/slot_length, on_holiday, action wake/skip |
| Reihenfolge | aufsteigend `(priority,name,id)`; Regeln vor Kalenderkonflikt; kein neues Punktesystem |
| Kalender | Skip nur ganztägig und vollständiger normalisierter Titel; Weckmarker über vorhandenes Regex und Zeitgruppe; ansonsten frühester zeitlicher Termin |
| Mehrere Marker | der letzte direkte Marker je Datum in übergebener Reihenfolge gewinnt; Skip ist im Original kein unbedingter Vorrang vor jedem Weckmarker |
| Feiertag/Urlaub | explizite Feiertage und manuelle volle/jährliche Datums-/Urlaubsintervalle; Wochenenden werden ebenfalls als frei behandelt; Samstag-Regel als Feiertagsrückfall |
| Untergrenze | lokale absolute Floor-Zeit; gilt auch für Kalendermarker und vorgezogene Termine |
| Fenster | symmetrisch `wake_time ± wake_window_minutes`, inklusive Grenzen im ursprünglichen Boolean; Fenster ist kein eigener Zustandsstart |
| Konflikte | ignore / warn_only / wake_earlier; Warnung verschiebt nicht |
| Suche | heute bis Tag +30 inklusive, nächster Kandidat `>= now`; gleiche Minute am Zeitpunkt zählt noch |
| Datenqualität | fehlende/ungültige Regeln, fehlender Floor, naive Uhr, falsches Kalenderdatum und optionale/alte Inputs getrennt diagnostizieren |

Die Vorlaufformel aus `_apply_calendar_conflict`, Zeilen 936–955, ist exakt:

`suggested_dt = local_event_datetime − timedelta(minutes=max(routine_duration_minutes,0))`.

Nur wenn `suggested_dt < bisheriger_Weckzeitpunkt` liegt ein früherer Konflikt
vor. `wake_earlier` baut die Tagesentscheidung mit der vorgeschlagenen lokalen
Uhrzeit neu auf und wendet erneut den Floor an. Synthetisch: Termin 06:30,
Routine 75 min → 05:15; Floor 06:00 → 06:00. Kein erfundener zusätzlicher
Vorlauf. Der Originalcode übernimmt bei einem über Mitternacht reichenden
Vorlauf die Uhrzeit wieder auf das Entscheidungsdatum. Der Port muss dieses
Verhalten im Vergleichstest sichtbar erhalten; eine Korrektur daran benötigt
einen gesonderten fachlichen Beschluss, kein stilles „Verbessern“ im Port.

Für den bestehenden UTC-Kalendercache übersetzt der Adapter vor dem Port
zeitliche Termine nach Europe/Berlin und ganztägige Intervalle zu lokalen
Datumsintervallen. Direkte Marker werden in der stabilen bestehenden Reihenfolge
`start,end,key` übergeben. Die 1:1-Grenze beginnt bei diesen normalisierten,
lokalisierten Eingaben, nicht bei rohen HA-Attributen. Keine Netzwerkabfrage im
Planoperator; ausschließlich der bestehende `ha_calendar`-Adapter liest Termine.

Strukturierter Parameter `wake_settings`, benanntes Schema `wake_planning_v1`:
genau zwei Profile mit Uhrzeit, Fenster, Mindestschlaf und provisional_lead;
bis 128 Regeln, bis 128 Feiertagsintervalle, bis 32 Skip-Titel, Weckmuster,
Routine 0–1.440 min, Konfliktverhalten und Floor. Identität/Anzeigenamen der
Profile bleiben erhalten. Provisional-Lead wird wie im Original gespeichert,
aber nicht zu einer neuen Vorlaufformel umgedeutet. Original-
`WakePlanningConfig.validated` normalisiert holiday_behavior auf
`weekend_profile`; die Oberfläche bietet deshalb keine scheinbar wirksame
Holiday-Skip-Einstellung an. Ein expliziter Skip bleibt als Regel möglich.
HA-Kalenderadressen sind Bindings, keine in den Port hinein kopierten
`calendar_entity`-Parameter. Migrations-/Rollbackdaten der alten Integration
gehören nicht in die neue Wuschel-Konfiguration.

Das allgemeine Parameterformat ergänzt in Sprachversion 6 ein Feld
`structured_schema` für Objektparameter. Nur im Backend registrierte,
versionierte und geschlossene Modelle sind erlaubt; zunächst allein
`wake_planning_v1`. Keine frei ausführbare JSON-Schema-/Python-Sprache, kein
externes `$ref`. Vorhandene skalare Felder bleiben unverändert. Profile und
Regeln sind damit echte Vertragsparameter und im Entwurf ohne Vorlagenversion
änderbar. Der spätere Schlummer-Editor benutzt denselben Backend-Parameterweg.

Wuschel validiert vor der Übernahme strikt: keine still entfernten ungültigen
Regeln, bool statt Zahl, NaN/Infinity, unbekannte Felder, doppelte Regel-IDs,
unvollständige Zyklus-/Wochenangaben, leere/ungültige Uhrzeiten oder Grenzen.
Der Originalparser bleibt für den Referenzvergleich unverändert, seine
tolerante Behandlung kaputter Konfiguration ist kein Import-Freibrief.
Kalender-Weckmuster maximal 256 Zeichen, Titel maximal 256 Zeichen, gesamter
Parameter höchstens 128 KiB. Der vorhandene Python-Regex-Dialekt und die
Zeitgruppenauswahl bleiben erhalten; gültige eigene Muster werden nicht auf
ein neues Glob- oder einfaches Markerformat reduziert. Ungültige Syntax oder
fehlende Zeitgruppe wird vor Übernahme sichtbar abgewiesen. Regex-Auswertung
erfolgt gemäß K4 inline: Syntax und Zeitgruppe werden bei der Übernahme geprüft,
Muster und Titel sind auf je 256 Zeichen, der Bestand auf 1.000 Termine begrenzt.
Es gibt keinen Arbeitsprozess, keinen neuen Service-Job und keine zugehörigen
Worker-/Abbruch-/Stale-Result-Tests. Der Pure-Port-Vergleich bleibt direkt.

## 7. Ausgabe, Ausnahme und Mindestschlaf ohne Zyklus (P5)

`wake.plan` veröffentlicht getrennt:

- `status`: heutige Tagesentscheidung `scheduled|skipped|holiday|inactive`;
- `next_wake_start`: nächster **effektiver** Zeitpunkt oder `not_applicable`;
- `plan_date`: Datum genau dieses Kandidaten;
- `window_start`/`window_end`: Fenster **desselben** Kandidaten;
- Evidence: Auswahlgrund, Regelkennung, Floor/Kalenderkonflikt,
  Mindestschlaf-Anwendung und Ausnahme, ausschließlich statische Codes/opake Keys.

Der heutige Skip darf also zusammen mit einem Termin für morgen erscheinen;
die Ansicht benennt „Heute ausgesetzt“ und separat „Nächstes Wecken“. Bei
fehlender gültiger Evidence sind betroffene Felder unknown, nicht gesund
inactive. `wake_needed` wird weder ausgegeben noch in Engines nachgerechnet.
Der Ablauf startet `waking` bei `next_wake_start`, nicht am Fensteranfang.

Die Basisentscheidungen und ihre heutigen Statuswerte bleiben Referenzergebnisse.
Danach folgen zwei **ausdrücklich von #61 geforderte Ergänzungen**, getrennt
von der 1:1-Prüfung: manuelle Ausnahme und Mindestschlaf.

Eine Ausnahme nutzt ADR 0016: optionale manuelle Objektquelle mit geschlossenem
Wertschema `{date:"YYYY-MM-DD",wake_time:"HH:MM"}` oder `{date,skip:true}`.
Sie gilt nur für dieses lokale Datum, Ende exklusiv am nächsten Tagesbeginn,
ist widerrufbar und hat keinen Effekt auf andere Tage. Sie überschreibt die
Basisentscheidung dieses Datums; danach gelten Floor und Mindestschlaf.
Kein neuer Status `overridden`: Ergebnis scheduled/skipped mit Ausnahme-Nachweis.
Die Eingabe „morgen“ wird im Formular zu einem konkreten Datum aufgelöst und
vor Absenden gezeigt. Diese Laufzeitquelle ist vom Parameterentwurf getrennt.
Ohne gültige Ausnahme zählt der Grundplan; Fehler bleiben als Einschränkung
sichtbar. Nach Neustart ist nur die noch gültige bestätigte Angabe nutzbar,
die Eingabezeit und ihr Ende werden nicht erneuert.

P5 benutzt einen **allgemeinen lokalen Zeitspeicher** des Ablaufs:
`first_sleep_at = erster tatsächlicher Eintritt in sleep innerhalb der Episode`.
Vorschlagsformat:

```json
{"captures":{"first_sleep_at":{"on_enter":"sleep","mode":"first_in_episode"}},
 "absolute_transition":{"states":["pre_sleep","sleep"],"target":"waking",
   "at_rule":{"op":"ref","name":"planned_start"},"priority":"absolute"}}
```

Eine neue Regel `machine_memory(slot)` liest nur diesen lokalen Speicherwert;
sie ruft niemals die Machine-Regel auf. `wake_plan` bekommt den Speicherwert,
die externen Kalender-/Datumsinputs und `wake_settings`, und kann typisierte
Felder per `field` auswählen. Der neue allgemeine `machine_field`-Zugriff liest
nach Abschluss Zustand/Metadaten für die Ausgänge. Er ist in Guards und
`at_rule` verboten. Das Backend prüft den internen Regelgraphen und diese
Phasengrenzen, zusätzlich zum unveränderten äußeren Zyklusverbot.

Vorgeschlagene Formatausschnitte, ausdrücklich keine heute gültige Registry:

```json
{"parameter_schema":{"wake_settings":{"schema":{"type":"object","required":true,
   "physical_state":false},"structured_schema":"wake_planning_v1"}},
 "rules":{"planned_start":{"op":"wake_plan","id":"plan",
   "settings_parameter":"wake_settings","date_input":"local_date",
   "calendar_input":"appointments","holidays_input":"holiday_days",
   "exception_input":"manual_exception",
   "sleep_since":{"op":"machine_memory","slot":"first_sleep_at"},
   "field":"next_wake_start"}},
 "outputs":{"value":{"op":"machine"},
   "since":{"op":"machine_field","field":"since_at"}}}
```

Weitere Planfelder verwenden dieselbe `id:plan` und identischen Eingangs- und
Parameteranschluss mit anderer geschlossener `field`-Auswahl. Validierung
verwirft widersprüchliche Anschlüsse derselben ID. Ein lokaler Memo-Eintrag je
ID, Eingabedigest und Capture-Generation hält den gesamten Plan; die Feldwahl
berechnet ihn nicht erneut. `machine_field` erlaubt nur deklarierte Felder
`since_at`, `entry_label`, `episode_id`, `episode_started_at`,
`episode_active`, `deadline_at` und die benannten Captures mit festem Typ.
Fehlender Capture/Termin ist `not_applicable`, ein unbrauchbarer bestehender
Speicher ist unknown. Der Operator unterscheidet beides ausdrücklich.

Feste Auswertung innerhalb **derselben** Processor-Transaktion:

1. Wiederherstellbaren committed Zustand samt Zeitspeicher laden; externe
   Eingangsvorgänge qualifizieren. Kein Wiederherstellungsereignis erzeugen.
2. Den einen zulässigen aktuellen Command-/Eingangsübergang anwenden und
   Eintrittsherkunft, Episode, Zeitspeicher und Frist gemeinsam ändern.
3. Grundpläne für heute bis +30 bilden, Ausnahme anwenden, für jeden noch
   relevanten Kandidaten Mindestschlaf anwenden, **danach** nächsten auswählen.
4. Gegen genau diesen Plan und die Dauerfrist entscheiden. Bei tatsächlichem
   Eintritt in sleep Speicher einmal setzen und Plan einmal erneut bilden.
   Diese Neuberechnung darf keinen zweiten Eingangsübergang auslösen. Bei
   `sleep → waking` bleibt der Speicher unverändert. Höchstens zwei Zeitübergänge
   (`pre_sleep → sleep → waking` bei bereits erreichtem Plan), keine Fixpunktsuche.
5. Alle Ausgänge aus dem finalen Zustand und finalen Plan erzeugen, gemeinsam
   committen, erst danach veröffentlichen und Clock-Alarme abgleichen.

Kein Delay-Vertrag, keine verdeckte Rückkopplung über eine manuelle Quelle,
kein Lesen des vorher veröffentlichten `sleep.state`, kein zweiter Plan in
Traber. Der bestehende memo-/due-Aufbau muss in Sprachversion 6 vor den
Ausgängen einmal zentral erfolgen; die Reihenfolge der JSON-Ausgabefelder darf
das Ergebnis nicht beeinflussen. Versionen 1–5 behalten den bisherigen Pfad.

Für einen geplanten Wecktag gilt Mindestschlaf nur, wenn dieser Tag Wochenende
oder Feiertag/frei ist. Der tatsächliche Schlafbeginn wird unabhängig von seiner
Herkunft verwendet. Kein Anker in pre_sleep; kein Anker aus Vermutung oder
Wiederherstellung einer rohen Sensorlage. In UTC:

`effective_start = max(base_start_after_exception_and_floor,
                       first_sleep_at + minimum_sleep_minutes)`.

Ohne gesetzten Mindestschlaf oder ohne tatsächlichen Schlafbeginn bleibt
der Basisbeginn. Das Fenster wird um denselben Unterschied verschoben und
behält seine konfigurierte Breite. Die Anpassung erfolgt **vor** dem
`candidate >= now`-Filter, sonst verschwände ein über seine Basiszeit hinaus
verschobener Wecktermin. Beispiel synthetisch: Samstag Basis 06:17, wirklicher
Schlaf ab 02:17, Minimum 480 min → 10:17, auch bei Auswertung um 07:17 weiter
derselbe Kandidat. Werktags bleibt 06:17. Bei neuer Episode wird der Anker
gelöscht; wiederholter Schlaf-Knopf verlängert die Frist, setzt ihn nicht neu.

Damit ein schon ausgelöster Termin beim erneuten Schlaf-Knopf während waking
nicht sofort wieder waking auslöst, merkt der allgemeine absolute Übergang
die verbrauchte Kandidatenkennung `(plan_date,base_start,plan_semantics)` je
Episode. Eine reine Mindestschlaf-Neuberechnung oder derselbe Restore
reaktiviert sie nicht; ein neuer Tag oder ausdrücklich geänderter Plan ist eine
neue Kennung. Der Plan zeigt den nächsten noch nicht verbrauchten Termin.
Änderung/Löschung ersetzt den Alarm; ein abgelaufener Callback einer alten
Frist-/Plangeneration ist wirkungslos. Diese Wiederholsperre ist expliziter
Reviewgegenstand, damit W4/W5 tatsächlich nutzbar bleiben.

## 8. Restore, Persistenz, Versionen und Fehler

Restore benötigt dieselbe geprüfte Semantikidentität, Zustand/Episode,
Originaltermine und neuen Zeitspeicher; kein `now + Dauer` beim Laden.
Ein schon fälliger Termin wird gegen aktuelle verwendbare TV-/PC-Evidence
geprüft. Bei fehlenden Fakten bleibt er unverarbeitet und sichtbar fällig.
Snapshots, Retained-MQTT, DB-Recovery, HA-/Wuschel-Neustart und Übernahme
erzeugen weder Interaktion noch Wecksignal noch Knopfdruck. Lücken dürfen
keine „frischen“ Kanten rekonstruieren. Der erste neue Zustand nach einer
Lücke setzt nur eine Baseline; eine folgende echte Änderung darf zählen.
Frische Ereignisse brauchen Originalzeit **nach** Zustandsbeginn und aktuelle
Epoch; ein verspätet eingetroffenes älteres Ereignis zählt nicht.

Bei unbekanntem TV/PC bleibt der interne Zustand erhalten; während einer
fälligen blockierten Frist gilt die vorhandene Diagnose `deadline_overdue`.
Weitere Gründe wie `input_stale`, `source_conflict`, Kalenderfenster außerhalb
des Nachweises und fehlende Herkunft werden nicht zu einem einzigen
„Schlafproblem“ zusammengezogen. Optionaler Ausfall erscheint degraded mit
seiner Ursache, blockiert aber nicht den ganzen Ablauf. Ein Commitfehler
veröffentlicht keinen neuen Zustand, keinen neuen Plan und keine Bestätigung.

| Version / Speicherung | A1-PR | Erwartung für A2 |
| --- | --- | --- |
| Programmversion | unverändert b10 | Ziel b11 erst im freigegebenen Bau-/Releaseweg |
| Regelsprache | unverändert 1–5 | additive **6** für neue Semantik und Operatoren |
| Registry-Schema | unverändert | **4 bleibt**, neue Definition trägt ihre Sprachversion |
| Fingerabdruck | unverändert | **4 bleibt**, neue Felder voll semantisch; alte fehlende Defaults ausgeschlossen |
| Portables Paket | unverändert | **2 bleibt**; Sprache/Fähigkeiten am Ziel vor Entwurf/Übernahme prüfen |
| Traber-Protokoll | unverändert | 2 bleibt, zusätzliche ausgehandelte Fähigkeit; alter Client erhält keine Anfrage |
| Datenbank | keine Änderung | **keine Migration erwartet**: Zeitspeicher/Planstatus in bestehendem JSON-Knotenzustand, Requests im bestehenden command_log, Ausnahme in manual_request/Observations |

Die neuen JSON-Laufzeitfelder benötigen eine lokale Formatkennung und sind nur
bei der neuen Definition vorhanden. Fehlen sie beim Restore einer schon
angelaufenen neuen Episode oder passt die Definition nicht, sichtbar
`restore_missing`/`restore_incompatible`, kein rückdatierter Schlafbeginn.
Noch nicht gestartete neue Vorlage initialisiert mit awake ohne Anker.
Registry-/Sprach-/Paketprüfung erfolgt auch beim Import alter Dateien;
unbekannte Sprache wird früh abgewiesen. Keine Bestandsdefinition wird beim
Lesen mit neuen Defaults gehasht oder auf Sprache 6 migriert.

Sollte A2 entgegen diesem Modell neue Tabellen oder eine inkompatible
Speicheränderung benötigen, muss zuerst der Designnachtrag samt Migration
reviewt und von Benni freigegeben werden. Vor einem solchen Release sichert
Benni LXC 108 selbst per vzdump; Codex prüft das Gate im Issue. A1 greift
auf keine Datenbank zu und erstellt keine HA-Sicherung.
